# Server security audit — 2026-09-22

Reviewed the working tree based on commit `11e07b9`. This was a focused manual review of server authentication, tenant isolation, HTTP routes, messaging permissions, report generation, automation, and database access. Reproductions used disposable SQLite databases, in-memory HTTP requests, and an embedded NATS broker; no deployed service or existing project data was modified.

All six identified findings are now fixed in this working tree and covered by regression tests. The fixes have not been deployed. Descriptions and reproductions below refer to the pre-fix behavior. Severity reflects the impact and stated prerequisites, rather than an assertion that a deployed instance has been compromised.

| ID | Severity | Finding | Status / evidence |

## A1 — Organisation administrator to SystemAdmin escalation (fixed)

**Original locations:** `server/rtdb/api/handlers_agent_tokens.go:104`, `:117`, `:131`, and `:279`; default grants in `server/sqldb/sqlite/sqlite.go:957`. Token retrieval at `handlers_agent_tokens.go:195` has the same privilege-boundary problem.

An account with `agentkeys.manage` may select another user's ID when creating an agent token. The handler copies that user's roles without checking whether the caller may grant those roles. The default `Admin` role has this permission. If a SystemAdmin belongs to the same organisation, its user ID can be selected and the newly returned bearer token inherits `SystemAdmin`. Existing SystemAdmin agent tokens in that organisation can also be retrieved through the management endpoint.

**Reproduction:** As an ordinary `Admin` in `default`, submit `POST /api/v1/agent-tokens/` with `{"name":"audit-elevation","userId":<SystemAdmin ID>}`. The response was HTTP 201 with roles `[SystemAdmin]`. Using that returned token to call the SystemAdmin-only organisation creation route also returned HTTP 201. All requests were local test requests with disposable data.

**Impact:** Full application administration across organisations, bypassing the user-management restriction that prevents an Admin from assigning SystemAdmin directly.

**Fix implemented:** A shared role-containment check protects both token issuance and raw-token retrieval. Only SystemAdmin can delegate roles they do not hold; other callers must hold every role carried by the token. This intentionally also blocks delegation to differently named roles, even when their configured permissions appear equivalent. Secret-bearing responses are marked `no-store`. SQLite-backed HTTP tests reject both escalation paths and confirm personal and SystemAdmin-authorized issuance still work.

## A2 — Shared NATS credentials and unrestricted JetStream access (fixed)

**Original locations:** `server/startup/main.go:134` and `:165` in the base commit; `/api/v1/system/nats-config` in `server/rtdb/api/server.go`.

Every authenticated account previously received the same browser password. Its broker permissions allowed subscriptions to every tenant's tree, broadcasts, KV subjects, and reply inboxes. Publishing to `$JS.API.>` also authorized stream administration, including delete, purge, and consumer management. These are administrative API subjects, as documented in the [official NATS JetStream API reference](https://github.com/nats-io/nats.docs/blob/master/using-nats/jetstream/nats_api_reference.md).

**Fix implemented:**

- Browser/mobile connections authenticate using their own HTTP bearer session. The shared `NATS_BROWSER_TOKEN` is ignored and no longer generated by the deployment script or required by production validation.
- Broker authentication validates the session against the database on every connection and reconnect. Existing user-session connections close at JWT expiry. Agent connections use their token expiry, or a 24-hour connection deadline for non-expiring tokens.
- Read permissions are limited to the current organisation and the HTTP role's tree/tag permissions. Mobile notifications are limited to the current user. Request inboxes are scoped to the bearer session.
- Browser JetStream, KV, and general publishing permissions are removed. Opt-in direct commands require tag-write permission and are limited to the current organisation.
- The config response is marked `Cache-Control: no-store`. The UI loads initial state through REST and receives live NATS updates without creating a KV bucket.

**Validation:** Embedded broker tests verify permitted tenant messages and command replies; rejection of other tenants, other users' notifications, other sessions' inboxes, legacy shared passwords, malformed tenant subjects, and destructive JetStream operations; and automatic disconnection at expiry. HTTP tests cover live account-state checks and config authorization. Relevant frontend tests cover credential/inbox setup, REST hydration, live updates, and subscription cleanup.

**Rollout:** Rebuild the UI and server and restart the server so existing broker connections are dropped. Refresh browser clients. This audit did not deploy or restart the running application. Account/role changes invalidate reconnections; an already-connected session can retain its granted permissions until expiry. Agent-token lifecycle checks are now covered by the A3 fix as well.

## A3 — Agent tokens survive account disablement and role revocation (fixed)

**Original locations:** `server/sqldb/sqlite/sqlite_orgs.go:477`, `server/sqldb/psql/postgres_orgs.go:507`, and `server/rtdb/api/middleware.go:91`.

Agent-token resolution checks the token hash and expiration but does not require an active owner, current organisation membership, or current owner roles. Authentication uses the stored role snapshot and replaces the owner identity with user ID `0`. User token-version changes therefore do not affect these tokens.

**Reproduction:** Create a personal token, disable its owner, and increment the user's token version. A subsequent protected request with the original JWT returned HTTP 401; the same request with the agent token returned HTTP 200.

**Impact:** A disabled or demoted account, or an attacker holding its token, retains the token's old privileges until token deletion or expiry. Expiry is optional.

**Fix implemented:** Both databases store the owner’s authentication version when issuing a token and require it to match during resolution, along with active ownership, membership, and expiry checks. Middleware intersects the role snapshot with live roles and preserves the owner ID. Account activation changes increment the version atomically; password, role, and session revocations also invalidate tokens. Agents cannot exchange these scoped credentials for user JWTs through organisation switching. The current-user organisation list respects their tenant scope, and personal profile/password endpoints require a user session.

**Migration:** Existing tokens receive version zero and fail closed; delete and reissue them after upgrading. SQLite tests exercise legacy-schema migration, reissuance, disable/re-enable, membership removal, demotion without a version bump, password/version changes, and expiry. Revoked credentials fail HTTP requests and NATS connection authentication.

## A4 — Reports disclose cross-tenant RTDB data (fixed)

**Original locations:** `server/rtdb/api/server.go:239`, `server/web/api/handlers_reports.go:283`, and `server/reporting/resolver.go:96`.

Report templates belong to an organisation, but RTDB variable paths are passed to a global tree reader without checking the requesting organisation. A report manager can reference a known tag under another tenant and render the value into a downloadable PDF.

**Reproduction:** A user in `default` created a template containing `{"name":"secret","type":"rtdb","path":"beta.device.secret"}` and placed `{{secret}}` in the document title. Creation returned HTTP 201, preview returned HTTP 200, and the resulting PDF contained the marker stored only under `beta`.

**Impact:** Disclosure of another organisation's live telemetry or other values stored in RTDB tags. It does not require access to the other organisation's report templates.

**Fix implemented:** The shared variable resolver validates and normalizes fully qualified dotted or slash-separated tag paths against `ResolveContext.OrgName` before calling any tag reader. Foreign, malformed, wildcard, and traversal paths resolve to an empty value without invoking the reader. The rule applies wherever shared resolution is used, including stored templates. Unit tests cover normalization and bypass attempts; SQLite-backed PDF preview tests confirm own-tenant values render and foreign values do not.

## A5 — MQTT authentication does not enforce tenant boundaries (fixed)

**Original locations:** `server/startup/mqtt.go:38` and `:47`; topic-derived tenant identity in `server/rtdb/ingest/mqtt/message.go:34`.

The broker accepts a single global password, ignores the username when authenticating, and grants every topic read/write permission. Ingest trusts the tenant component supplied in the MQTT topic. A client possessing the broker password can subscribe to other tenants' data or publish forged data to `xact/data/<other-tenant>/<device-type>/<device-name>`.

**Prerequisite:** Access to the embedded broker and its shared password. Outside production mode, an unset password falls back to the known value `xact`; production validation rejects that default, but does not address tenant isolation.

**Fix implemented:** Devices authenticate with their tenant slug and an ingest API key belonging to that tenant. Client IDs must use `<tenant>:<device-id>` to prevent persistent-session takeover across tenants. ACLs permit only own-tenant data publishing and own-tenant data/control subscriptions; foreign wills, cross-tenant wildcards, and shared subscription prefixes are rejected. Key ownership is rechecked for authorization, including delivery. The internal ingest subscriber has a separate random process-local credential, read-only access to the ingest topics, and a reserved client ID. Shared passwords and the known development fallback are removed from the embedded broker.

**Validation and rollout:** In-process tests exercise the actual MQTT broker, valid delivery to both tenants and the internal subscriber, denied subscription and publication paths, credential misuse, client-ID takeover attempts, will restrictions, and key-revocation/error handling. Configure devices with tenant API keys and prefixed IDs before reconnecting. Bundled demo, benchmark, and AirQuality clients and documentation were updated. External brokers require equivalent operator-managed ACLs; this fix configures the embedded broker.

## A6 — Public first-run admin setup can be claimed remotely (fixed)

**Original locations:** public routes at `server/rtdb/api/server.go:356`; password setup at `server/rtdb/api/handlers_auth.go:147`; unset-password fallback at `server/sqldb/bootstrap.go:49`.

When the bootstrap admin has no configured password, any network client can call the public setup endpoint with a chosen password and receive an admin JWT. No setup secret, authenticated operator, or trusted local channel is required. Production secret validation does not require a bootstrap password. The read/check/write sequence also lacks an atomic claim operation.

**Prerequisite:** A new or otherwise unclaimed installation is reachable before its operator completes setup. This does not reset an admin password that is already configured.

**Fix implemented:** Browser setup requires the operator-provided `XACT_BOOTSTRAP_SETUP_TOKEN` (at least 32 characters), compared in constant time. An absent/short token disables setup. Both databases atomically update only an active, unset `admin` account, so only one claim succeeds and an existing password cannot be overwritten. The UI requires the token and explains disabled setup; bootstrap responses are marked `no-store`. The deployment script generates a random setup token for new packages. An initial password can still be provisioned before a fresh database is seeded.

**Validation:** SQLite-backed HTTP tests reject missing/wrong operator tokens and confirm exactly one success and one conflict for concurrent claims. PostgreSQL mock tests verify the conditional update and fail-closed error handling. Frontend tests verify the setup-token request and disabled setup state.

## Validation and limits

- Full server suite passed: `go test -mod=mod ./...`. Existing NATS and MQTT TLS listener tests required local-listener access outside the restricted sandbox; new broker security tests use in-process connections.
- Focused API and MQTT security tests passed with the Go race detector.
- All 54 selected UI tests passed; TypeScript passed with `--noEmit`, and the Vite production build succeeded.
- Changed LTA/traffic-image demo tests and AirQuality tests passed; the benchmark package compiled (no tests).
- A1, A3, A4, and A6 now have regression tests against actual SQLite-backed HTTP handlers with synthetic accounts and data. Legacy agent-token migration was also tested. PostgreSQL implementations and mock tests passed, but no live PostgreSQL service was exercised.
- Dependency CVE scanning was not completed: `govulncheck` was not installed and building its cached versions required unavailable dependency versions. This report does not assert that dependencies are free of known vulnerabilities.
- This was not an exhaustive penetration test or a review of production network/reverse-proxy configuration. No deployed instance was modified. No speculative SQL injection or remote-code-execution claim is included: reviewed SQL paths used parameters, and shell/Yaegi scheduler execution is gated by an explicit unsafe-task setting.

## Upgrade requirements

Rebuild and deploy the server and UI, restart the server, and refresh browser clients. Reissue existing agent tokens; configure MQTT devices with tenant API keys and tenant-prefixed client IDs. For an unset admin password, supply an operator setup token or provision an initial password before creating a fresh database. See `ui/public/manual/02-preparing-for-production.md` for configuration details. Existing NATS connections can retain grants until expiry; restarting drops them during rollout.
