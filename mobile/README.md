# XACT Mobile

Flutter client for XACT operations. It uses the same JWT login, organisation
context, UI permissions, REST endpoints, report engine, and NATS WebSocket
interface as the web application.

## Run locally

Install an Android SDK, make it visible through `ANDROID_HOME`, then run:

```bash
flutter pub get
flutter run
```

The login screen accepts either a host name or URL. A host without a path is
normalised to `https://<host>/xact`; an explicit reverse-proxy path is kept.
HTTPS is required for the API and downloads, and WSS is required for NATS.
URLs with embedded credentials, query strings or fragments are rejected as
server addresses. Development servers also need trusted TLS certificates.

## Deploying the security update

Deploy the updated server and web UI before the mobile app. Embedded dashboards
require the server's inert `/api/v1/mobile/bootstrap` document and the UI's
`embedded=dashboard` session-storage mode. Background push requires the
`sessionScopedPush` capability in the server's Firebase configuration response.
Older servers cannot provide secure dashboard bootstrap or background push;
foreground NATS notifications and REST polling remain available.

Account changes cancel old requests, discard navigation history, clear browser
storage/cookies/cache, and delete cached reports and APKs before a new session
starts. Reports explicitly exported to another application remain under that
application's control. Notification and dashboard preferences are scoped to
server, user and organisation. The old device-wide notification preference is
removed on upgrade, so users must opt in again.

## Android APK

```bash
flutter build apk --release
```

Release builds require a dedicated production signing key. Create an untracked
`android/key.properties` file with the following deployment-specific values:

```properties
storeFile=/secure/path/xact-release.jks
storePassword=<keystore password>
keyAlias=<production alias>
keyPassword=<key password>
```

Keep the keystore and its passwords outside source control and restrict access
to them. The build rejects missing signing configuration and Android debug
identities. No production key is supplied or generated by this project.
Existing installations signed with the old debug certificate cannot accept an
ordinary update signed with a different production key; plan a managed
reinstallation for those devices.

To publish a self-hosted update through XACT, configure the server with:

```dotenv
MOBILE_APP_VERSION=1.0.1
MOBILE_APK_URL=/downloads/xact-mobile-1.0.1.apk
MOBILE_RELEASE_NOTES=Maintenance and reliability improvements
```

The APK URL may also be absolute, but must use HTTPS. The app sends the API
bearer only to the API's exact origin, rechecking each redirect. External hosts
receive no API credentials; use a public artifact or a separately authorised,
short-lived download URL. Downloads are streamed into a dedicated private cache
directory with a 256 MiB limit and a two-minute timeout. Before opening the
Android installer, the app requires its own package name, a higher version code,
and the same current signing certificates as the installed app. Signing-key
rotation requires a separately planned migration; this update flow does not
accept a new signer automatically.

## Notifications

Opt-in is stored in the signed-in user's existing `notificationOptions` as
`mobileEnabled`. Foreground delivery continues to use the organisation-scoped
NATS mobile subject, with REST polling as a compatibility fallback.

For background Android push, register the Android application in the same
Firebase project used by the server's FCM notification channel. The distributed
APK contains no deployment-specific `google-services.json`: it loads the public
Firebase options from the selected XACT server and initializes Firebase at
runtime. The app registers and refreshes its project-bound FCM token in the
signed-in user's notification options automatically. Push notifications open
the related device when tapped.

New registrations include a random session binding. The updated server sends
data-only messages for these registrations; foreground/background handlers and
notification taps require a matching, unexpired secure-storage session before
showing content or opening a device. Logout clears that local authority first,
removes the matching remote registration when reachable, clears displayed
notifications, and deletes the Firebase token. Offline logout still rejects
queued messages locally. Legacy clients retain their old server payload format
and must be upgraded to receive these protections.

The Android package name registered in Firebase must be
`com.xact.iot.mobile`. Obtain `google-services.json` from Firebase **Project
settings > General > Your apps** and paste it into **Android
google-services.json** under **Notifications > Channels > Android Push (FCM)**.
Separately, generate a server service-account JSON key from **Project settings >
Service accounts > Firebase Admin SDK** and paste it into **Service Account
JSON**. The service-account document contains a private key and must never be
returned to the app or committed to source control.

The server exposes only the non-secret Android project ID, application ID, API
key, and Messaging Sender ID. Native Android startup persists and restores these
options so terminated-app notifications work. Switching to a server that uses a
different Firebase project triggers one automatic app restart.
